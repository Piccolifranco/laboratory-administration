# pnpm Migration — Design

**Date:** 2026-05-28
**Branch:** `feature/pnpm-migration` (off `development`)
**Status:** Design pending implementation plan
**Predecessor:** [Dependency upgrade](./2026-05-28-deps-upgrade-design.md), shipped 2026-05-28 via PR #1.

## Goal

Switch the laboratory-administration project from **npm** to **pnpm 11.4.0**, with zero behavioral change to the app and zero deploy-config change on Vercel. Migration is performed on the post-dep-upgrade `package.json` (secure versions, with the `overrides` block for postcss). The `pnpm-lock.yaml` produced here is the first lockfile generated by pnpm against the upgraded tree.

## Scope

**In scope:**
- Pin pnpm 11.4.0 via `packageManager` field in `package.json` so corepack auto-installs it on first use.
- Add `engines.node: ">=22.0.0"` so Vercel and any future contributor get a consistent Node version (current LTS).
- Mirror the existing npm `overrides` block under `pnpm.overrides` so pnpm honors the postcss override that fixes Next 16's nested vuln.
- Convert `package-lock.json` to `pnpm-lock.yaml` via `pnpm import` (preserves the resolved-version graph — no drift).
- Delete `package-lock.json` and `node_modules/`, then `pnpm install`.
- Update `README.md` from npm command examples to pnpm command examples.
- Verify locally and on the Vercel preview build.

**Out of scope:**
- Dependency version changes of any kind (those shipped in the previous PR).
- pnpm workspaces (single-app repo).
- Custom `.npmrc` / `.pnpmrc` tweaks unless step 5 (verify) surfaces a real need.
- Switching off corepack (e.g., requiring a global pnpm install).

## Design decisions

### pnpm 11.4.0 (not 10.x)

Franco's explicit preference. pnpm 11 introduced:
- `managePackageManagerVersions: true` by default — pnpm reads `packageManager` from `package.json` and self-installs the pinned version. This is the behavior we want anyway.
- Tighter resolution defaults. If a transitively-relied-on hoisted package breaks, the fix is a `public-hoist-pattern` entry in `.npmrc`, decided only if we hit it.

### Corepack-managed, not global

`corepack enable` (already available with Node 22+) ensures the pinned `packageManager@version` is installed on demand. No global `npm install -g pnpm` step. Vercel's build runners support corepack natively.

### Node 22 LTS pin

Franco's choice. Locks `engines.node` to `>=22.0.0`. His local Node 24 satisfies this; Vercel will resolve to the latest 22.x for the build runner. Conservative for production; doesn't lock anyone out who's on a current LTS.

### Override mirroring

The deps-upgrade PR added:
```json
"overrides": {
  "postcss": "^8.5.15"
}
```

npm reads `overrides`. pnpm reads `pnpm.overrides`. To make the override survive the migration cleanly, this spec **mirrors** the block under both keys. Leaving only one would either (a) work today but break if Franco ever runs `npm install` again, or (b) work today but lose the override the moment pnpm regenerates the lockfile.

```json
"overrides": { "postcss": "^8.5.15" },
"pnpm": {
  "overrides": { "postcss": "^8.5.15" }
}
```

## Migration steps (one commit each)

### Step 1 — `package.json` edits (no install yet)

- Add `"packageManager": "pnpm@11.4.0"` (pinned to the exact version, not a caret range — corepack treats the pin literally).
- Add `"engines": { "node": ">=22.0.0" }`.
- Add `"pnpm": { "overrides": { "postcss": "^8.5.15" } }` mirroring the existing `overrides` block.

Commit.

### Step 2 — Enable corepack and convert the lockfile

- Run `corepack enable` to make corepack pick up the `packageManager` pin.
- Run `pnpm import` in the project root. This reads `package-lock.json` and emits `pnpm-lock.yaml` preserving the exact resolved-version graph (no drift relative to what shipped in PR #1).
- Stage `pnpm-lock.yaml` only — do not yet delete `package-lock.json` (we want to verify the install before throwing away the npm lockfile).

Commit.

### Step 3 — Switch over

In this order:

1. Delete `package-lock.json` (the npm lockfile — `pnpm-lock.yaml` is now authoritative).
2. Delete `node_modules/` (the npm-symlinked one).
3. Run `pnpm install` — materializes a fresh `node_modules/` from `pnpm-lock.yaml`.
4. Verify: `pnpm run build` succeeds; `pnpm run lint` runs to completion; `pnpm audit` shows zero HIGH/MODERATE.
5. Manual smoke test of the critical path (login, patient list, search, patient detail, create-visita, generate one PDF of each available report type).

If verification fails: `git reset --hard HEAD~1` reverts to the Step 2 commit (which still has both lockfiles); investigate and re-attempt.

Commit the deletion of `package-lock.json`.

### Step 4 — README update

- Replace `npm` command examples in `README.md` with `pnpm` equivalents.

Commit.

### Step 5 — Open the PR and verify on Vercel

- Push branch, open PR against `development`.
- Confirm the Vercel preview build (a) detects pnpm via `pnpm-lock.yaml`, (b) builds successfully, (c) the deployed preview passes the critical-path smoke test.

## Risks

| Risk | Likelihood | Mitigation |
|---|---|---|
| A package misbehaves under pnpm's stricter isolation (some packages assume hoisted access to transitive deps) | Low-Medium | Stays a build/runtime error if it appears; fix is a `public-hoist-pattern=*PKG*` entry in `.npmrc`. Decide only if observed. |
| Vercel doesn't pick up the pnpm lockfile | Very Low | Vercel auto-detects via `pnpm-lock.yaml` + `packageManager` field. Documented as supported. |
| `pnpm import` resolves slightly different versions than the current npm lockfile | Low | `pnpm import` is specifically designed to preserve resolutions. If the graph differs, the deps-upgrade PR was the place to lock versions — verify via `npm audit` after Step 3. |
| The `pnpm.overrides` block doesn't take effect (postcss vuln returns) | Low | `pnpm audit` after Step 3 will surface this immediately. Fix: ensure the `pnpm` field is at the top level of `package.json`, not nested elsewhere. |

## Done criteria

1. `package-lock.json` is gone; `pnpm-lock.yaml` is committed.
2. `package.json` has `packageManager`, `engines.node`, and mirrored `pnpm.overrides`.
3. `pnpm run build` and `pnpm run lint` succeed.
4. `pnpm audit` shows zero HIGH/MODERATE.
5. Vercel preview build succeeds on the PR.
6. Manual smoke test passes on the Vercel preview URL.
7. `README.md` reflects pnpm commands.

## Non-goals (explicit)

- No source-code changes. This is a tooling-only migration.
- No dependency version bumps. The dep tree is exactly the one that shipped in PR #1.
- No `.npmrc`/`.pnpmrc` customization unless observed-needed.
- No Vercel-side config change.
