# Doctor's Signature on PDF Reports — Design

**Date:** 2026-05-28
**Branch:** `feature/pdf-signature` (off `development`)
**Status:** Design approved, pending implementation plan
**Predecessors:** [Deps upgrade](./2026-05-28-deps-upgrade-design.md), [pnpm migration](./2026-05-28-pnpm-migration-design.md).

## Goal

Add Dra. Carolina Lorena Vadillo's signature image to every PDF medical report generated by the laboratory-administration app. The signature is the direct, client-stated reason for this whole modernization round.

## Scope

**In scope:**
- Add a new asset `public/images/doctor_signature.png` (a transparent-background PNG of the signature, converted from the PDF Franco has).
- Modify [src/app/ui/pdfComponents.tsx](../../../src/app/ui/pdfComponents.tsx) to render the signature on all three report types: `PapDiagnosisComponent`, `CepilladoDiagnosisComponent`, `BiopsiaDiagnosisComponent`.
- Add a `signature` style entry to the existing `StyleSheet.create(...)` block.

**Out of scope:**
- A data-driven signature (e.g., per-visit `secondaryDoctor` signature). There is only one doctor for this clinic.
- A caption / printed name under the signature.
- Gating by report type — the signature appears unconditionally on all three.
- Multi-page-specific logic — react-pdf's natural flow handles placement.
- Touching the existing fixed footer (microscope logo).
- Any change to the data model, visit type, or PDF callers.

## Design

### Asset

A new file at `public/images/doctor_signature.png`. Format: PNG with transparent background, so the signature sits cleanly on any page color. Source: Franco converts the existing PDF version of the signature to PNG. Target source resolution ~600–800px wide is more than enough at 300 DPI for the rendered size.

The file lives in `public/images/` to match the existing pattern (the microscope logo is at `public/images/microscope_logo.png`). Next.js auto-serves `public/`; `@react-pdf/renderer`'s `<Image>` component fetches via the `src` prop using the absolute path `/images/doctor_signature.png`.

### Placement

The signature is rendered **inside the body of the document, after the last text line of the diagnosis, before the closing `</View>` of the section block**. This means:

- For short diagnoses, the signature appears on page 1 right after the diagnosis text.
- For long diagnoses that span multiple pages, the signature naturally lands on the last page along with the diagnosis tail.

No page-break logic is needed; react-pdf's normal flow renders content sequentially, so whatever page the closing `</View>` lands on is where the signature ends up.

### Style

Add one entry to the existing `StyleSheet.create(...)` block at the top of `pdfComponents.tsx`:

```ts
signature: {
  width: 150,
  marginTop: 30,
  alignSelf: "flex-end",
},
```

- `width: 150` — approximately 53mm in print, a typical professional signature size. Height is derived automatically from the source image's aspect ratio (no `height` property needed).
- `marginTop: 30` — gives breathing room between the last diagnosis line and the signature.
- `alignSelf: "flex-end"` — right-aligns the signature within its parent `View`. Conventional for formal medical documents.

### Component edit pattern

Each of the three report components receives the same edit: an `<Image>` element added just before the final `</View>` of the inner `styles.section` View. Example for `PapDiagnosisComponent` — the change is the last line before the closing `</View>`:

```tsx
<Text style={styles.content}>Nota: {visita[visita.type]?.notes}</Text>
<Image src="/images/doctor_signature.png" style={styles.signature} />
</View>
```

Identical pattern for `CepilladoDiagnosisComponent` and `BiopsiaDiagnosisComponent`. The signature is the last element inside the body section, after the notes field.

The existing `<View style={styles.svgContainer} fixed>` block holding the microscope logo stays unchanged — it's a separate fixed footer on every page.

## Verification

This project has no automated test suite. Verification is visual:

1. Generate one PDF of each report type (Pap, Cepillado, Biopsia) using a real patient/visit from local data.
2. Confirm the signature appears right-aligned, sized appropriately (not pixelated, not tiny, not so large it overlaps other content), and on the same page as the last diagnosis line.
3. Confirm the microscope-logo footer still renders unchanged on every page.
4. If any of those visual checks fail, tune `signature.width` or `signature.marginTop` — both are single-number changes.

## Risks

| Risk | Likelihood | Mitigation |
|---|---|---|
| The PNG conversion has a non-transparent (white) background, putting a visible rectangle around the signature | Medium | Pre-verify the PNG in any image viewer before placing it in `public/images/`. If wrong, redo the PDF-to-PNG conversion with explicit transparency. |
| Signature ends up on a fresh page alone because the last diagnosis section ends right at the page boundary | Low | If observed during visual verification, reduce `marginTop` or trim the signature width slightly so it fits. |
| Image looks pixelated at the rendered size | Low | Use a source PNG ≥ 600px wide. 300 DPI at 53mm rendered = ~625px source. |
| Signature image is too large in print | Low | One-line change: lower `signature.width` until it looks right. |

## Done criteria

1. `public/images/doctor_signature.png` exists, transparent background, source resolution ≥ 600px wide.
2. `pdfComponents.tsx` has the new `signature` style and one `<Image>` element in each of the three report components.
3. All three PDF report types generate cleanly with the signature visible at the bottom of the document body, right-aligned.
4. The existing microscope-logo footer is unaffected.
5. `pnpm run build` succeeds.
6. PR opens against `development`, Vercel preview build succeeds, the deployed preview generates correct PDFs.

## Non-goals (reaffirmed)

- No backend changes — same client-direct Supabase flow.
- No new dependencies.
- No new data model fields or migrations.
- No changes to other PDF components (e.g., `DocumentoPDF.tsx`) beyond what's needed to render the modified report components.
- No conditional logic gating the signature by visit type or doctor identity.
